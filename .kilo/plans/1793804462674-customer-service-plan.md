# 客服系统改造计划

## 目标
将现有 AI 智能伴侣改造成客服系统：先命中知识库，未命中时由 AI 回答（带领域边界）；支持多租户座席/后台与监控数据。

## 范围与阶段
1. Phase 1（MVP）：客服对话链路
   - 知识库检索优先；未命中时 LLM 回答
   - LLM 回答限制在客服/业务领域，禁止编造
2. Phase 2：座席与后台
   - 多租户权限模型（tenant + admin/agent/user）
   - 座席控制台（会话分配、回复、转人工）
3. Phase 3：监控与运营
   - 会话/消息量、知识库命中率、AI 质量与成本指标

## 现有基础
- `src/framework/ai/aicompanion_v2` 已集成 RAG（`chat_service.py` 调用 `kb_service.search_similar`）
- `src/framework/ai/knowledge_simple` 提供文档上传与检索
- `src/app/clients/studentmanage_v2` 提供 FastAPI 路由与鉴权模式可复用

## 数据流
1. 用户消息 → 知识库检索（top_k + threshold）
2. 命中 → 返回知识库片段 + 来源
3. 未命中 → LLM 回答（系统提示限制领域，无资料时明确说明）
4. 全链路记录会话、消息、检索命中与 token 用量

## 关键设计
- 多租户：所有表增加 `tenant_id`，鉴权基于 JWT/Session
- 边界：系统提示 + 检索上下文；未命中时固定话术“暂无资料，转人工/补充知识库”
- 监控：新增 metrics 表或聚合查询，前端仪表盘

## 风险
- 多租户数据隔离需严格校验
- LLM 成本与延迟，需限流与缓存
- 知识库质量影响回答准确性

## 验证
- 单元测试：检索命中/未命中分支、边界话术
- 集成测试：端到端对话 + 多租户隔离
- 监控接口返回聚合数据

## 开放问题
- 租户创建与计费策略
- 座席并发与会话分配算法
